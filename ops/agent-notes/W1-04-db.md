## 0. Fix round (2026-09-23) - the one audit item attributed to this package

`ops/agent-notes/wave1-audit.md` reports **no red artefact** for `W1-04-db` (lint clean, every `src/main/db/**` test green,
no typecheck error in an owned file). The only item routed back here is the ORCHESTRATOR / W2-01 question about
`chats.mergeLidInto` vs CONTRACTS 15.1. This round **confirms the reading and hardens the one case where the original
implementation was genuinely unsafe.** Files touched: `src/main/db/repos/chats.ts`, `src/main/db/repos/chats.test.ts`. Nothing else.

**The conflict, restated precisely.** CONTRACTS 15.1 asks `mergeLidInto` to "move the @lid row's items/actions" to the surviving
phone-JID row. That is not implementable against the frozen schema, for two independent reasons:

1. `trg_actions_frozen` (CONTRACTS 15.2, frozen DDL) lists `chat_id` among the immutable columns, so `UPDATE actions SET chat_id=?`
   aborts. This is safety **I3** working as designed: the recipient is pinned at proposal time and an approval can never be re-aimed.
2. `actions.chat_id INTEGER NOT NULL REFERENCES chats(id)` has **no `ON DELETE` clause**, so the rows cannot stay behind either -
   with `foreign_keys=ON` the `DELETE FROM chats` that the same contract sentence demands would fail.

So an action row of the @lid chat can only be **destroyed** with the chat row. ARCH 4.6 step 4 already says only
"merges an older @lid row **and its items**" - i.e. the architecture and the code agree, and the CONTRACTS sentence is the outlier.
**Confirmed: items-only is the correct reading.** Proposed amendment (orchestrator's call, `docs/specs/contracts.md` is not an owned
path here):

> `mergeLidInto`: "... move the @lid row's **items** to it, drop the @lid row's own action rows, and delete the @lid row ...
> (`actions.chat_id` is frozen by `trg_actions_frozen` - safety I3 - so an action can never follow its item into another chat).
> The merge is deferred while one of those action rows is `approved` or `executing`."

**Why destroying them is acceptable - and where it was not.** An @lid chat is not sendable, and `agent/validate.ts:174` gates
`send_reply` on `chat.sendable`, so the only action kind that can exist on an @lid chat is `create_event`. For a row in
`pending`/`rejected`/`expired`/`superseded` no side effect ever happened; for `done`/`failed`/`unknown_outcome` the evidence does not
live in the row anyway - `audit_log` is append-only (`action_approved`, `action_done`, `action_failed`, `action_reconciled`, written by
`exec/actionExecutor.ts` and `exec/reconcile.ts`) and `items.calendar_event_id` moves with the item. **But `approved`/`executing` is a
side effect in flight**, and the old code deleted those too: that dropped the UNIQUE `idempotency_key` and the row
`exec/reconcile.ts` needs to find out whether Google already holds the event, and left the executor's `markDone`/`markFailed` to hit a
missing row. That was a real (narrow) hole, in an owned file.

**Fix:** `mergeLidInto` now **defers** - it returns the @lid chat unchanged, mutating nothing - while
`COUNT(*) FROM actions WHERE chat_id = ? AND state IN ('approved','executing') > 0`. It is bounded: within a session the executor
settles the row, and `ActionExecutor.recoverOnStartup()` turns every `executing` row into `unknown_outcome` at the next start, so the
merge can never be blocked for more than one app life. `unknown_outcome` is **not** in the defer set (it is in
`TERMINAL_ACTION_STATES`; blocking on it could postpone the merge forever when the calendar is disconnected). Callers tolerate a
deferral: `ingest.handleChat` sets `effectiveJid` to the phone JID either way, and `ingest.resolveLidChats` retries on the next ONLINE
transition (its `merged` counter is one too high in that rare tick - cosmetic, W1-03's file, not changed from here).
The doc comment on the method was also **wrong** before this round ("superseded while still pending") - no supersede ever ran. Fixed.

Two new tests in `repos/chats.test.ts` (11 in that file now, 152 in `src/main/db/**`): the deferral + the merge succeeding once the row
is settled, and a settled-only @lid chat merging normally. `src/main/db/**` coverage after the change: 97.82 % stmts / 91.92 % branch /
98.47 % lines (thresholds 90/85/90). `npm run typecheck` is clean repo-wide; `npx eslint src/main/db --max-warnings 0` is clean.
`npx prettier --check src/main/db` still warns on 25 files - **pre-existing**, unchanged by this round, and the repo-wide Prettier pass
is W2-01's by ownership (audit section 2.3), so it was deliberately not run here.

## 2. Decisions and assumptions (each one is a place a reviewer may disagree)

1. **`items.state` has exactly one writer.** `updateItemRow()` in `repos/items.ts` loads the row, applies the defined patch keys,
   recomputes `state = deriveState()` and bumps `updated_at`. `recoverRunning`, `expireOld` and the LID merge in `repos/chats.ts`
   all go through it rather than issuing their own `UPDATE ... SET state`.
2. **`closed_at` follows `closed_reason`.** Closing without an explicit `closedAt` stamps `now`; re-opening (`closedReason: null`)
   clears it. An explicit `closedAt` in the patch always wins.
3. **`expireOld` measures the 7 days from `trigger_ts`** (the newest triggering message, which ingest bumps on every new inbound
   message) and the "past" rule from `event_start_ts + 24 h`. ARCH 7 says "open > 7 days" without naming the column;
   `created_at` would expire a conversation that is still alive, `updated_at` would be reset by internal writes.
4. **`counts()`** counts the four states over `analysis IN ('done','held','failed')` and reports `queued + running` as
   `analysing` (ARCH 6.1: queued/running items are counted, not listed).
5. **`settings.get()` never throws.** A row that no longer satisfies `SettingsSchema` (downgrade, hand-edited file, restored old
   backup) falls back to `DEFAULT_SETTINGS`; the stored row is left untouched so the deviation stays visible. `patch()` validates
   with `SettingsPatchSchema` first, so an unknown key or a channel-only field (`llm.provider`, `agent.paused`, …) is rejected.
6. **`queue.defer(lastError)` stores an `ErrorCode` or NULL.** The parameter is typed `string`, so anything that is not a member of
   `ERROR_CODES` is dropped instead of persisted - a provider/zod message can echo attacker-controlled text (CONTRACTS 1, ARCH 10).
7. **`markApprovedExecuting` maps every miss to `'stale'`**, including a trigger `ABORT` (node:sqlite `ERR_SQLITE_ERROR`). A
   non-SQLite error is re-thrown, so a real defect is never swallowed as a lost race (there is a test for exactly that).
   `markRejected` does NOT throw on a miss: CONTRACTS scopes the `ActionStateError` rule to `markDone/markFailed/markUnknownOutcome`,
   and a double reject must not crash the IPC handler.
8. **Retention counts**: `textRows` = nulled `item_messages` rows + nulled `proposals` rows; `actionRows` = distinct action rows
   that lost `canonical_json` and/or `approved_final_json` (counted with a `SELECT COUNT(*)` because the two columns must be
   nulled by two separate statements - `trg_actions_frozen` fires on the *column list* of the `SET` clause, so nulling
   `canonical_json` on a row where it is already NULL aborts).
9. **Backup file names**: `app-YYYYMMDD.db` (UTC), `app-YYYYMMDD-HHmmss.db` when that name is taken (a pre-migration and a daily
   copy on the same day), plus a counter if even that collides. Rotation and `newestBackup` order by **mtime**, not by name,
   because `-` sorts before `.` and a name sort would misorder the two shapes. `keep` defaults to **3** (brief + TESTS 5.3);
   the W0 stub comment said 7 and was wrong.
10. **Pre-migration backup**: `openDb()` derives `<dirname(appDb)>\backups` and skips the copy for `:memory:` and for a file whose
    schema is still empty (a fresh install has nothing to lose). A failing copy never blocks the upgrade - the migration itself is
    transactional. With only migration v1 on the books this path is unreachable through `openDb`, so it is exported as
    `backupBeforeMigration()` and unit-tested directly.

## 4. REQUESTS

Addressed to the package id that owns the file. None of these were changed by W1-04.

- **ORCHESTRATOR (spec owner)** - *[updated 2026-09-23, see section 0]* amend the `mergeLidInto` sentence in CONTRACTS 15.1 to the
  wording quoted in section 0 (items-only + drop the @lid chat's action rows + defer while one is `approved`/`executing`). The code is
  right, the spec sentence is the outlier; ARCH 4.6 step 4 already says "and its items". No code change is needed if the amendment is
  accepted. If instead the orchestrator wants actions to follow their item, that is a **frozen-DDL change** (`trg_actions_frozen` would
  have to stop protecting `chat_id`), which reopens safety I3 and is not a W1-04 decision.

- **W2-01-compose-integration (and the spec owner)** - *[original wording, kept for the record]* `repos.chats.mergeLidInto` cannot do what CONTRACTS 15.1 says.
  Its doc comment asks to "move the @lid row's items **and actions**" to the surviving phone-JID row, but `trg_actions_frozen`
  (CONTRACTS 15.2, frozen) lists `chat_id` among the immutable columns, so any `UPDATE actions SET chat_id=...` aborts - and safety
  I3 (the recipient is pinned at proposal time) is the reason that trigger exists. ARCH 4.6 step 4 says only "merges an older @lid
  row **and its items**". Implemented: items move, `is_known`/`force_known` are OR'ed, the @lid chat's own action rows are deleted
  with the row (an `@lid` chat is not sendable, so at most a `create_event` action can exist there, and `items.calendar_event_id`
  keeps the link to the created event; the audit log keeps the record). Please either confirm this reading or amend CONTRACTS 15.1.
- **W2-01-compose-integration** - register a slow-statement handler at startup:
  `setSlowStatementHandler((s) => log.warn('db_slow_statement', { op: s.op, ms: Math.round(s.ms) }))`. Nothing is measured until a
  handler is registered, and nothing is reported when `NODE_ENV === 'production'`. Please do not log `s.sql` verbatim in packaged
  builds even though it carries only static SQL.
- **W2-01-compose-integration** - prefer `openDbWithRecovery(paths.appDb, paths.backupsDir)` over a bare `openDb()`; it already
  implements "restore newest backup, else start empty" and tells you which of the three happened for the `DB_RECOVERY` toast and
  the `db_recovery` audit row.
- **W1-11-exec** - `ActionStateError` is exported from `src/main/db/index.ts` (declared in `src/main/db/errors.ts`). `chainRoot(id)`
  returns the **root action**; `stripRetrySuffix(root.idempotencyKey)` is the `chainKey` that `eventIdFor()` needs.
- **W1-03-bridge-ingest** - `repos.actions.supersedePendingRepliesOfChat(chatId, exceptItemId, now)` only supersedes `send_reply`
  rows of that chat's *other* items; `create_event` rows and the new item's own draft are untouched, which is what ARCH 4.6 step 6
  describes. Call it inside the same `repos.db.transaction()` as `items.createOpen`.

## 7. Dead ends / things deliberately not done

- A `toRun()` row mapper was written and then removed: `runs` is write-only from the app's side (aggregate reads only), and dead
  code in a safety-relevant module is worse than a missing convenience.
- `openDb()` was NOT given extra parameters (a logger, a backups dir) - its signature is frozen by CONTRACTS 15.1. Hence the
  module-level slow-statement handler and the `<userData>\backups` derivation.
- No index, trigger or column was added to `migrations.ts`: the DDL is frozen and migrations are append-only. `migrations.test.ts`
  only reads it (tuple-vs-CHECK parity).
- `purgeNow` does not shorten the 90-day closed-item window or the 180-day metadata window; ARCH 10 says it runs "the same job with
  `retentionDays=0`", and the metadata tables hold no text.
