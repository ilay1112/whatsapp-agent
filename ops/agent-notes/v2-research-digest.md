## claude-cli-backend

**Recommendation:** Use the user's Claude Pro/Max subscription by spawning the user-installed, unmodified Claude Code CLI (claude.exe, native installer at %USERPROFILE%\.local\bin\claude.exe, observed version 2.1.258) directly via child_process — do NOT add the Agent SDK dependency and do NOT bundle the binary. Every call: `claude -p --input-format stream-json --output-format stream-json --verbose --no-session-persistence --restricted --disable-slash-commands --tools "" --strict-mcp-config --permission-mode dontAsk --disallowedTools "<bash/edit/web/agent list>" --max-turns N --effort low|medium --model sonnet --fallback-model haiku --system-prompt-file <file> [--json-schema <draft-07>] [--mcp-config <tempfile> --allowedTools "mcp__wa__*"]`, run in an empty app-owned working directory, with ANTHROPIC_API_KEY/AUTH_TOKEN/PROFILE/cloud-provider env vars stripped so the subscription OAuth (precedence rank 7) is used. Never use --bare (it never reads OAuth). Send the user message (text + optional base64 image block) as one JSON line on stdin; parse the stream-json `system/init` (assert tools list, MCP status), `rate_limit_event` (resetsAt, isUsingOverage) and final `result` (check is_error FIRST, then subtype==='success' and structured_output present). Host the app's read-only MCP server as loopback HTTP with a per-run bearer token in a 0600 temp config file so ToolGate stays in the Electron main process and the same server serves Gemini. Detect with `claude --version` (require >= 2.1.221) and `claude auth status --json` (parse only `loggedIn`); sign-in is done by launching Anthropic's own `claude auth login --claudeai` flow, never by the app. Keep the API-key provider as the advanced fallback and keep providers pluggable because of Anthropic's April-2026 third-party-harness enforcement.

**Risks:**
- Policy/enforcement: Anthropic blocked third-party harnesses from Pro/Max subscriptions on 2026-04-04 and 'may enforce without prior notice'; a community project spawning the Agent SDK as a subprocess reported being affected (mechanism UNVERIFIED). Our unmodified-CLI, single-user, own-login path fits the documented carve-out, but the provider must stay pluggable and the API-key fallback must remain.
- Auto-updating native install means flags/semantics can change under the app (docs say --bare 'will become the default for -p in a future release', which would break subscription auth); mitigate by version-gating, asserting system/init.tools, and a tiny smoke run at provider start.
- Headless error reporting is inconsistent (issue #79500 open: is_error true with subtype success and exit 0); wrappers must classify on is_error + result text + api_retry events, never on exit code alone.
- Shared usage windows: a chatty background pipeline can exhaust the user's own claude.ai/Claude Code 5-hour window; usage percentages are not available headlessly; usage credits (isUsingOverage) cost real money at API rates.
- UNVERIFIED items that need a one-time smoke test with the user's login: image input over stream-json on the raw CLI, exact `claude auth status --json` fields beyond loggedIn, whether `--json-schema` accepts a file path (assumed not), `--setting-sources ""` acceptance on 2.1.258, minimum version for --restricted, rate_limit_event status values other than 'allowed'.
- Tool-less --json-schema calls hit the $PARAMETER_NAME self-heal bug (~27% first attempts, extra round-trip/usage); either accept it or keep the confined Read tool enabled.
- Windows process control: child.kill() does not kill the CLI's MCP/child process tree; use taskkill /T /F; the loopback MCP bearer token must go in a temp file (not the command line) and be deleted after each run.

**Open:**
- Should the read-only run keep the confined `Read` tool enabled (avoids the --json-schema placeholder-key bug and doubles as the image fallback) or stay strictly tool-less?
- Which model should be the default for S1/S3 on subscription (sonnet recommended; Opus 5.5 is the plan default but burns the 5-hour window and may be unavailable on Pro)?
- Does the user's plan (Pro vs Max) matter for the per-hour call cap in settings, and should the app expose resetsAt from rate_limit_event in the status bar?
- Should the app verify the Authenticode signer ('Anthropic, PBC') of claude.exe before spawning (cheap integrity check; UNVERIFIED that the launcher stub is signed)?
- Loopback HTTP vs stdio for the app MCP server: HTTP keeps ToolGate in-process and serves Gemini too, but requires a listening port on 127.0.0.1 with a per-run token — acceptable under the security posture in ARCHITECTURE.md?

## gemini-cli-backend

**Recommendation:** The user's belief is verified exactly: on 2026-06-18 the open-source Gemini CLI stopped serving Google-login requests for free, Google AI Pro and Google AI Ultra accounts (announced 2026-05-19; "Login with Google" removed for consumers), and those tiers moved to Antigravity CLI (`agy`, Go binary, currently 1.2.12). Gemini CLI (npm 0.61.0) still works only with a Gemini API key, Vertex AI, or a Code Assist Standard/Enterprise business seat; it has no custom-schema flag (issue closed "not planned" 2026-05-06). The only no-API-key subscription path is `agy -p ... --output-format json --json-schema <file> --agent <name> --model <slug> --print-timeout Nm --disable-slash-commands`, run as a child process with `stdin: 'ignore'` in an app-owned trusted workspace, using the Google login cached in Windows Credential Manager; the Antigravity IDE exposes no external API and the new Antigravity SDK is API-key/Vertex only. That path is a policy gray zone: Terms §6 and the FAQ forbid "third party software, tools, or services" accessing the service (ban wave precedent 2026-02-27), while forum answers from the Antigravity team (staff badge unverified) called single-user unmodified-binary headless use "permitted"/"a supported workflow" (7 and 15 Sep 2026) but said `agy -p` "cannot be used to power third-party agents" (25 Sep 2026). Recommendation: build the agy backend as opt-in "Gemini via Antigravity CLI (experimental)", OFF by default, with an in-app §6 + data-use disclosure; run it tool-less (custom agent `tools: []`, `commandExecutionPolicy: off`, `excludeDefaultComponents: true`, app injects read-only context itself, `--json-schema` structured output validated by S4, one process at a time, hard kill), version-gate agy >= 1.2.11, and keep the v1 API-key Gemini provider as the officially supported path (D-038 fallback). Do not attach MCP tools to agy in v2 (open bugs #548/#794 plus the 25 Sep policy wording); exact command lines and the TypeScript wrapper shape are in sections 8.1-8.5 of the report.

**Risks:**
- Account risk: Antigravity Terms §6 lets Google suspend the user's Antigravity and Gemini CLI accounts for third-party tool use; forum 'supported' statements are not the Terms, their authors' staff badges are unverified, and the 25 Sep answer explicitly excludes 'powering third-party agents'. The feature must be opt-in with disclosure and the API-key provider must remain.
- Headless tool use in agy is unreliable: #548 (permissions ignored, silent stall past --print-timeout) and #794 (schema + denied tool reported as SUCCESS) are open; any MCP-tool variant is deferred and the wrapper must treat a missing structured_output or non-empty denied_actions as failure and hard-kill with taskkill /T.
- UNVERIFIED items needing a smoke test on the real binary with the user's login: image delivery via @path in -p (blocker for D-039 pictures on Gemini), AGY_ERROR field names, denied_actions shape, /usage JSON fields, agy models output format, Credential Manager entry name, whether the trust gate still blocks headless runs on 1.2.x, and whether deleting the run's brain/<conversation> dir is tolerated.
- Privacy: agy writes every prompt (role-labelled WhatsApp text) to ~/.gemini/antigravity-cli/brain/.../transcript.jsonl and Google may use Interactions to improve products unless opted out in Antigravity settings; the user's global MCP/hooks config is loaded in every run (hooks receive transcriptPath/modelName), so tools: [] and an explicit consent record are mandatory.
- The CLI self-updates almost daily and flag semantics drift (docs already stale on the default timeout; 1.2.11 only just fixed workspace agents in headless); the app must set AGY_CLI_DISABLE_AUTO_UPDATE=true per run, version-gate >= 1.2.11, and assert init.tools / structured_output at runtime rather than trusting the docs.
- Quota sharing: background pipeline runs draw down the same five-hour/weekly Antigravity window the user uses interactively, with no published numbers; Pro/Ultra overage credits cost real money if 'AI Credit Overages: Always' is set - run one process at a time and surface /usage in the status bar.
- Eligibility: Antigravity is only for personal Google accounts 18+ in approved regions; Workspace accounts may be blocked regardless of AI Pro - the app must treat 'not installed / not logged in / not eligible' as normal states with the API-key fallback.

**Open:**
- Does the orchestrator accept shipping the agy backend at all given the 25 Sep forum wording, or should v2 ship Gemini as API-key only and keep agy behind a hidden/experimental flag until Google publishes a clearer policy?
- Should the tool-less agy path reuse the exact v1 S1/S3 prompts (recommended) or a shorter variant to stay well under the ~55 KB prompt size where headless print mode has been seen to hang (#947)?
- Pictures on Gemini (D-039): if the @path smoke test fails in -p mode, fall back to local vision for images even when Gemini/agy is the active cloud provider?
- Who owns the one-time setup step that adds the app workspace to trustedWorkspaces in the user's ~/.gemini/antigravity-cli/settings.json (read-merge-write with consent), and is editing a user config file acceptable under ARCHITECTURE.md's security posture?
- Which Flash slug should be the default (gemini-3.8-flash-medium for extract, -high for draft is proposed) and should the settings model list come live from `agy models` at settings time?

## cli-mcp-bridge

**Recommendation:** Host the app's read-only tools as a Streamable HTTP MCP server INSIDE the Electron main process (node:http on 127.0.0.1, port from proc/freePort, per-run 32-byte bearer token, SDK 1.30.0 StreamableHTTPServerTransport in stateless mode with enableDnsRebindingProtection + allowedHosts ['127.0.0.1:<port>'], our handler rejecting any Origin and returning 404 on bad tokens), one listener per run, closed in finally. The server IS ToolGate: it registers exactly gate.exposedSpecs() from a single zod-first toolDefs table (LLM JSON derived once via z.toJSONSchema(args,{target:'draft-07'}) + toLcd(), frozen by the I4 test; MCP registerTool takes the same zod shapes), and every tools/call goes through ToolGate.invoke() unchanged (budgets, strict args, pinned window/chat handles, projection, nonce wrap). Claude Code (installed 2.1.258, require >= 2.1.221) runs headlessly as: claude -p --restricted --strict-mcp-config --mcp-config '{"mcpServers":{"wca":{"type":"http","url":...,"headers":{"Authorization":"Bearer ${WCA_MCP_TOKEN}"}}}}' --tools "" --allowedTools "mcp__wca__*" --disallowedTools <bare deny list> --permission-mode dontAsk [--permission-prompts none >= 2.1.259] --disable-slash-commands --no-session-persistence --system-prompt <verbatim S1/S3> --model sonnet --effort low --max-turns N --output-format stream-json --verbose [--json-schema], prompt on stdin, empty temp cwd, allow-listed env (ENABLE_TOOL_SEARCH=false, DISABLE_* switches, never ANTHROPIC_API_KEY/CLAUDE_CONFIG_DIR), shell:false spawn of the resolved claude.exe, and a fail-closed assertion of the system/init event (mcp_servers == [wca], tools subset of mcp__wca__*, no plugins). Never --bare (never reads OAuth). Antigravity CLI (agy, latest 1.2.12; the subscription route since Gemini CLI was cut off 2026-06-18) ships in v2 in NO-TOOLS mode (custom agent file with tools: [] and commandExecutionPolicy: off; the app prefetches free/busy and WhatsApp context through the same ToolGate and inlines them in the nonce block; --print-timeout always set; init.tools asserted empty) because headless permission handling is broken (issues #548, #916 open) and there is no strict-mcp/tools-off flag; the MCP-to-agy recipe (workspace .agents/mcp_config.json with serverUrl + literal header, permissions.allow ["mcp(wca/*)"] merged with a shown diff) is kept as a v2.1 variant. Per-run contract: same nonce data block as v1, LIMITS.cliWallClockMs 120 s (S3) / 60 s (S1), abort = child.kill() then taskkill /PID /T /F via the v1 supervisor helper, concurrency 1, CLI-refused tool names audited as v1 tool_blocked rows (sha8+len only, 2 strikes -> kill + manipulation), new cli_run audit kind. Provider contract gains loop:'turn'|'agentic'|'prefetch' and runAgentic(); auto mode is allowed with the Claude CLI provider (zero built-in tools proven by init) and with Antigravity only when init.tools asserts empty.

**Risks:**
- Claude Code auto-updates itself; --bare may become the -p default and flag semantics can drift - mitigated only by version floors, the per-run system/init assertion and a tolerant stream-json parser (U8), not eliminated.
- UNVERIFIED U2: with --tools "" and ENABLE_TOOL_SEARCH=false, the mcp__wca__* tools must appear in system/init.tools; if tool search still hides them or --tools "" removes the MCP path, the S3 run has no tools - needs one user-run smoke with the real login before build.
- UNVERIFIED U9: system/init.apiKeySource literal for subscription OAuth is unknown, so 'the run used the subscription, not an API key' is currently guaranteed only by the env allow-list.
- Antigravity in no-tools mode cannot let the model choose what to look up (the app decides the prefetch window); the model-driven search->context pattern of the D-036 delta case works only on Local/API-key/Claude CLI until #548/#916 are fixed and the v2.1 MCP variant is verified (U4).
- Antigravity persists headless conversations under ~/.gemini/antigravity-cli/brain (U5) and the user's global mcp_config.json registers the reference WhatsApp MCP with send_message; no-tools mode neutralises the latter but the former needs consent text; the Terms section 6 wording leaves account-suspension risk with the user.
- Anthropic's subscription policy flipped three times in 2026; the 2026-06-15 pause could end - keep providers pluggable, keep the API-key fallback, map authentication_failed/oauth_org_not_allowed/account_on_hold to a visible CLOUD_AUTH state.
- A loopback listener with a bearer token is open for up to 120 s per run; DNS-rebinding protection and Origin rejection are in the design but Windows Defender firewall behaviour for the packaged app's node:http listener is unverified (U11).
- Both CLIs share the user's own quota windows (Claude 5-hour/weekly; Antigravity compute-based 5-hourly/weekly); a chatty pipeline can lock the user out of their own tools - concurrency 1 plus the existing per-hour LLM caps are the only brakes.

**Open:**
- Should the loopback tool server be per-run (this report) or a long-lived listener with a token registry while a CLI provider is active (whatsapp-mcp-readonly)? Both satisfy the 404-after-run guarantee; per-run is recommended for lifetime simplicity.
- Confirm the MCP server name 'wca' (vs 'wa' / 'waagent' in the sibling reports) so Claude rules (mcp__wca__*) and Antigravity rules (mcp(wca/*)) are consistent everywhere.
- Keep the v1 LCD schema subset (ranges in descriptions + execute) or extend the LCD to allow minimum/maximum/minLength/maxLength for all three backends?
- Should automatic mode (D-037) be selectable while antigravity_cli is the active provider at all in v2, given init.tools assertion (U4) is unverified until the user runs the smoke test?
- Which model defaults on subscription: sonnet for S1/S3 (recommended) and which Antigravity Flash slug (gemini-3.8-flash-high proposed; silent-downgrade bug #687 means the JSON result never names the model)?
- Who owns the fake claude.exe / fake agy.exe scripted-attacker CLIs for the e2e handshake test (proposed: the cli-mcp-bridge build lane builds them, toolserver tests consume them)?

## event-editing

**Recommendation:** Implement D-036 as a linked-item delta pipeline over the existing S1-S4 + executor: extend the single flat S1 schema with refersToExisting / change (no_change|reschedule|move|cancel|new_event) / changeConfidence, inject the app-computed existing event inside the nonce data block (never its eventId), resolve the delta deterministically in S2 (inherit date/time from the trusted event, nearest-hour disambiguation), persist it on the NEW open item ingest already creates (linked_item_id, proposals.delta_json, update_event action with targetEventId + baseRevision pinned), and execute it through a new executor-only McpWriteClient.updateEvent with an exhaustive whitelist, pre-flight get-event (drift / gone / foreign), readback-verified done, event_revisions audit and one-click undo through the same approval path. Before build, the orchestrator must take one decision (D-042 candidate): the stock @cocal/google-calendar-mcp@2.6.3 update-event has NO status field and silently strips it, so "cancel = status cancelled" requires either a 2-line vendored patch of the bundle (recommended, sha256-pinned + fail-closed startup guard, plus an upstream PR) or a soft-cancel fallback (summary prefix + transparency:transparent). Also add get-event to ENABLED_TOOLS (read class, never exposed to the LLM) because cancelled events are invisible to list-events.

**Risks:**
- Vendored patch of a minified bundle is fragile: a version bump can silently invalidate it — mitigated by a sha256 pin (build fails) and a startup inputSchema guard (CAL_TOOLSET_MISMATCH), but it is a maintenance burden until upstream accepts a `status` field.
- Google 'cancelled' means deleted: undo of a cancel depends on patch {status:'confirmed'} restoring the event (documented as restorable, exact API behaviour UNVERIFIED) and on Google's retention of trashed events (window UNVERIFIED); the design falls back to re-creating the event with a new id.
- 4B local model accuracy on the new `change` field for terse Hebrew is unmeasured; false positives like 'בוא נזיז ל-5' vs 'אנחנו 5 אנשים' rely on the prompt addendum + S2 cross-checks; the golden live gate must pass before the delta path is enabled by default per provider.
- Two items per event while a change is pending (source in_calendar item + new needs_reply item) can show the event twice unless the renderer keys the calendar list by calendar_event_id.
- extendedProperties.private patch semantics (merge vs replace) and whether location:'' clears the field are UNVERIFIED; mitigated by always sending the full private map and by accepting a stale location as fallback.
- Migration v4 is a multi-table rebuild with trigger re-creation; a mistake there corrupts approval invariants — needs a v3 fixture round-trip test and the section-18 consistency tests.

**Open:**
- Decision needed (D-042 candidate): express 'cancelled' via the vendored `status` patch of the MCP bundle (recommended) or via soft-cancel (summary prefix + transparency:transparent) — or accept both with a startup-chosen CANCEL_MODE?
- Should the golden edit cases live in a new tests/golden/edits.jsonl or be spread across he/en/mixed (affects the per-language count assertions in golden.test.ts)?
- Automatic mode (D-037) gating for deltas: is `changeConfidence==='high'` + no manipulation/conflict/change_unclear badge the agreed threshold, and should the re-create fallback of an undo also be auto-applied?
- Should T-401 be closed by the proposed rule (an edited retry of a create whose chain-root event is found becomes an update_event instead of a second create)?
- Is one editable event per chat (the newest in_calendar) acceptable for v2, or must two live events in one chat be disambiguated?

## auto-mode-safety

**Recommendation:** Ship automatic mode only behind a DB-enforced policy model. I1 becomes I1': "no WhatsApp send without a per-action click; no calendar write without EITHER a per-action click OR an auto_decisions row bound to this action and to a live, natively-confirmed auto_policies row", enforced by the actions trigger through a new approved_by column (decision id, never a bare 'auto' constant) - not by an `if`. Add a pure, LLM-free AutoGate in exec/ with an exhaustive AUTO_REASONS enum whose every failure falls back to the v1 approval card with the reason shown. Cage every automatic write: own calendar with accessRole exactly 'owner' (CalendarInfo gains the raw role; absent = not owned), no attendees, sendUpdates:'none' on create AND update (server default is 'all'), app-template description, horizon <= 30 d, 5 min-4 h, not sooner than 15 min (create) / 2 h (edit), never delete, edits only to app-tagged events whose waItem = the linked SOURCE item of the same chat with creator.self and unchanged updated/etag, <= 2 edits per event, move <= 14 d, cancel off by default. Auto sub-budgets (1/30 min, 2/h, 3/day per chat; 4/h, 15/day global) with circuit breakers that pause the policy (any budget hit, 2 undos/24 h, any unknown_outcome, 7 days unattended, snapshot change, calendar disconnect). Eligibility: is_known (not force_known), zero badges, no blocked tool call, no assumed hour, confidence/changeConfidence 'high', never media-derived (picture/voice) in v2.0, never from a vendor-CLI run whose system/init.tools assertion did not pass. Shadow (dry-run) is the default first state and never switches itself on. Every auto write: app-text-only toast with an Undo button (Electron 44.4.3 has Windows toast actions) + dashboard "Automatic" card; pre-write snapshot stored in the same transaction as the write-ahead (auto_writes.pre_json), undo through the editing design's single item:undoChange path over event_revisions; readable "Automatic activity" page + export; toggle reachable only via a dedicated IPC channel from a focused window confirmed by a main-owned native dialog.showMessageBox (Cancel as default/cancel id, required checkbox), 30-day expiry. Before the event-editing build: decide F1 (vendored patch adding `status` + `If-Match` to @cocal/google-calendar-mcp 2.6.3 update-event; the read side needs no patch) and merge this document's approved_by/tryAuto design with v2-event-editing.md section 3.5.

**Risks:**
- F1 unresolved: without the vendored patch (status + If-Match on update-event) cancel and undo-of-create can only be the editing design's soft cancel; a vendored patch of the minified bundle must be sha256-guarded and re-applied on every server upgrade, and it invalidates the v1 tool-list hash pin until updated.
- Residual accepted by D-037: a known contact can still cause a bounded, undoable add/move on the user's own calendar within 30 days; the misleading-title residual (T13) exists until the user sees the toast/card; 'unattended' detection is heuristic (window focus).
- D-038: auto mode is safe only when the vendor CLI run provably had no tools beyond the app's read-only MCP; Claude Code CLI supports this (--tools "" --strict-mcp-config + system/init.tools assertion) but the Gemini CLI equivalent is UNVERIFIED - auto must stay unavailable with Gemini CLI until shown.
- Cross-document conflict to record as one decision: v2-event-editing.md section 3.5 sketches approved_by IN ('user','auto') DEFAULT 'user' and an AutoApprover calling executor.approve() with a fake IpcContext; this document supersedes it (decision-id binding verified by the trigger; approve() stays click-only). It also corrects the editing doc's aside that a post-undo re-create is 'auto-applied' - it runs under the user's Undo click, never through AutoGate.
- UNVERIFIED: events.patch merge-vs-replace semantics for extendedProperties.private (mitigated by always sending the full map; confirm in the packaged smoke test with a dummy event); AppUserModelID/Start-menu-shortcut prerequisite for toast button activation on a clean Windows 11 VM; release dates of the Electron backport minors (the release-page summary returned implausible dates).
- Product friction: shadow/trial, per-chat budgets (3/day) and the never-auto rules for media-derived and badge-carrying items may make the mode feel like 'approval with extra steps'; reasons are shown on the card, and the user-echo/user-participation heuristics are SHOULD-only until measured in shadow.
- Migration risk: the auto tables plus actions.approved_by must ship in the same CHECK-constraint table rebuild as the editing migration; a torn rebuild relies on the runner's pre-migration backup and needs a v3-fixture round-trip test.

**Open:**
- Q1: Decide F1 - vendored patch (editing doc's two insertions + this doc's ifMatch insertion) vs soft cancel; needed before D-036 cancel semantics and undo-of-create.
- Q2: Confirm events.patch preserves/merges extendedProperties.private in the packaged smoke test (dummy event only).
- Q3: Confirm Windows toast action buttons activate the packaged Electron 44.4.3 app (AppUserModelID + shortcut) on a clean Windows 11 VM.
- Q5: Does Gemini CLI offer a hard built-in-tool disable equivalent to Claude Code's --tools ""? Until verified, auto mode unavailable with the Gemini CLI provider.
- Q6: Product - should reschedules to a different day be automatic at all (cage allows <= 14 d; same-day-only is a one-line scope change)?
- Q7: Hebrew copy for the native enable dialog and the AUTO_REASONS strings.
- Q8: Orchestrator to record the merge of this document's approved_by = decision id / tryAuto design over v2-event-editing.md section 3.5 as one decision.

## whisper-local

**Recommendation:** Ship voice-note transcription as a short-lived `whisper-cli.exe` job (not a 4th resident child) from the official whisper.cpp CPU zip `whisper-bin-x64.zip` at nightly tag `b5130` (= stable v1.9.4, 2026-09-11; 8,573,270 B, sha256 f9ec6c52a2e949b62ab51fa21d0d497958f9e41c3010c157c4e42932d5316f3c; MSVC build, same VC++ CRT dependency as llama-server, packaged by explicit allow-list into `resources/whisper/`; no official Windows Vulkan zip exists, CUDA zips are 270-675 MB). Default voice tier `hebrew` = `ivrit-ai/whisper-large-v3-turbo-ggml/ggml-model.bin` (f16, 1,624,555,275 B, sha256 c8090411…, Apache-2.0) with forced `-l he` (the card says language detection is degraded), because on the ivrit.ai leaderboard's WhatsApp set it halves OpenAI turbo's WER (0.071 vs 0.128); alternative tiers `multilingual` = `ggml-large-v3-turbo-q8_0.bin` (874 MB, `-l auto`) and `lite` = `ggml-small-q8_0.bin` (264 MB); no medium (slower, no Hebrew evidence), no distil (English-only), no q5_0 (3-5x slower on CPU). Always run Silero VAD `ggml-silero-v6.2.0.bin` (885,098 B, MIT) with `--vad --vad-threshold 0.5 --vad-min-silence-duration-ms 400 --vad-speech-pad-ms 60 --vad-max-speech-duration-s 30`, plus `-oj -of <tmp> -np -nt -bs 5 -bo 5 -tp 0 -et 2.4 -sns -t max(2,min(8,cores-2))`, BELOW_NORMAL priority, minimal env, stdout ignored, stderr marker-filtered. Audio source: the bridge already auto-downloads every incoming audio message to `<userData>\bridge\store\<jid>\audio_<ts>_<msgId>.ogg` and records the name in `messages.filename`; the app reads it read-only after a realpath-prefix + regex guard, waits up to 30 s, and only then uses `POST /api/download` as a narrow fallback (requires an explicit A16 amendment). Decode Ogg Opus to 16 kHz mono PCM16 WAV with `opus-decoder@0.7.12` (MIT, libopus WASM embedded in the JS, deps @wasm-audio-decoders/common MIT, simple-yenc MIT, @eshaz/web-worker Apache-2.0) fed by an app-authored ~150-line Ogg demuxer (RFC 3533/7845; code shape in section 7.2) and a 30-line WAV writer; do NOT use `ogg-opus-decoder` (its demuxer `codec-parser@2.5.0` is LGPL-3.0-or-later and it drags in an 8 MB opus-ml package), no ffmpeg, no native addons. Transcription runs inside `orchestrator.runChat` before S0 so it shares the TriageQueue's concurrency of 1 with llama-server; transcripts are cached in an `app.db` table `transcripts (chat_jid, wa_msg_id, status, text, language, seconds, model_label, ...)`, treated as UNTRUSTED message text (sanitised, nonce-wrapped DATA block with `source:'voice_transcript'`, never in the system prompt), timeout = clamp(30 s, 4 x audio seconds x bench factor, 10 min), 15-minute hard cap, models downloaded through the existing ModelManager with new tiers (`voice-hebrew|voice-multilingual|voice-lite|voice-vad`, magic `GGML` = bytes `6c 6d 67 67`, verified for both whisper and VAD files). Nothing leaves the machine.

**Risks:**
- UNVERIFIED: opus-decoder@0.7.12 import and decoding under Electron 44's Node (ESM, embedded WASM string; whether @wasm-audio-decoders/common touches Worker/window at import) - must be probed in Wave 0 like node:sqlite was; peak memory on a 15-minute note (~58 MB Float32) is estimated, not measured.
