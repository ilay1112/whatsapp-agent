# Design critique findings (workflow ①, 3 critics)

Raw findings as returned; the finalizer decides which to apply. Orchestrator back-fill 2026-09-22.

## critic:requirements — 11 findings

- **[major]** ARCHITECTURE.md A14 + 4.6 step 3; agent-pipeline.md 1.3 step 2 (backlog gate: `now - ts > 24 h at ingest => context-only`)
  - Problem: The absolute 24 h rule silently drops real live messages on the target device (a laptop that is closed over a weekend or the app quit for a day). Messages delivered by WhatsApp on reconnect arrive as ordinary rows with their original timestamps, not as history sync, so 'coffee Sunday at 5?' sent Friday night and read Monday morning never becomes a 'Needs reply' card and is never shown at all. This defeats the core personal-assistant requirement for exactly the laptop profile the product targets.
  - Fix: Apply the 24 h age cap only to rows that arrive while the bridge is (re)syncing history (between spawn and the `History sync complete` marker) or before `live_from_ts`; for rows that arrive after the bridge was ONLINE at least once, use `ts >= meta.last_online_ts - grace` (or simply 7 days) as the trigger cutoff, and list anything older-but-live as a raw card with an 'older message' chip instead of dropping it. Persist `meta.last_online_ts` on every ONLINE->offline transition. Add a golden test: message ts = now - 3 days, bridge was online yesterday => item created.
- **[major]** ARCHITECTURE.md A12/A13 + 4.6 steps 3-4 (`@lid` copy-only; `is_known = EXISTS(messages WHERE chat_jid=? AND is_from_me=1)`); bridge-contract.md section 7
  - Problem: In 2026 many DM contacts arrive under `<digits>@lid`, and the same person can be split into an `@lid` chat and a phone-JID chat (bridge-contract 7, lharries/whatsapp-mcp #198). Under this design such a contact is (a) copy-only, so the 'reply' requirement is not met for them, and (b) 'unknown' because the user's outbound rows live under the phone JID, so the chat is held as `unknown_sender` and never analysed. Two independent gates combine to make the assistant do nothing for an unknown but possibly large share of contacts, and the bridge's startup LID->PN rewrite (chat JIDs 'may CHANGE between runs') is not handled by `chats.jid UNIQUE` keyed state at all.
  - Fix: 1) In ingest, resolve `@lid` chats to the phone JID via a read-only lookup of the bridge `chats`/`whatsmeow_lid_map` mapping (or the `SenderAlt` the bridge already persists) and key `chats` on the phone JID when a mapping exists; re-run that resolution on every bridge ONLINE transition and merge items. 2) Compute `is_known` over both JID forms of the contact. 3) Promote V3 (`POST /api/send` with an `@lid` recipient) from 'later, with a test contact' to a release-gate manual item; the bridge already accepts any full JID, so if it works extend `DM_LID_JID_RE` to sendable and drop copy-only. 4) Record the expected `@lid` share after the first supervised launch in ops/PROGRESS.md.
- **[major]** ARCHITECTURE.md A9/A10, 5.3, 5.4, 6.4 (S3 runs only when `needsReply`; freebusy prefetch happens inside S3; create-event executed by ActionExecutor without the LLM)
  - Problem: The locked decision says Google Calendar 'connectivity should run by the LLM via MCP' with the server's tools exposed to the active LLM. In the design the LLM only ever sees three app-authored READ wrappers, and only inside S3 DRAFT, which is skipped when `needsReply=false`. For the 'confirmation' path (golden he-04/en-04: the contact agrees to a slot the user proposed) no LLM turn touches the calendar and no free/busy prefetch happens, so the event card carries no `conflict` badge and the user first learns about a clash at click time via `needs_confirm_conflict`. The create path never involves the LLM at all. This is a defensible approval-first reading, but it is a visible deviation from the requirement wording and it produces worse UX on the most common calendar case.
  - Fix: 1) Move the app-side `get_freebusy` prefetch out of S3 into S2/S4 so it runs whenever a complete slot exists (calendar connected), independent of `needsReply`; badge `conflict` from it. 2) Record an explicit decision in ops/DECISIONS.md, confirmed with the user, that 'LLM via MCP' means read-only tool calling by the LLM plus app-executed `create-event` through the same MCP client after approval; add one sentence to the README/onboarding privacy table. 3) Optionally let S3 also run for `event_state='proposed' && !needsReply` with a 'no reply needed' directive so the LLM can still check alternatives via tools (keeps the requirement literally true).
- **[major]** ux.md 8.2 (3 phone illustrations), 8.3 (five annotated Google Cloud Console screenshots `google-N.webp` + the 'Google hasn't verified this app' picture), 8.4 and 12.2 (Windows 11 hidden-icons flyout picture in light/dark x LTR/RTL); build-plan.md W1-16 owns `resources/onboarding/**`

Remove `resources/onboarding/**` from the ownership matrix and the electron-builder `extraResources` entry, and change the `alt`/`data-testid` acceptance items accordingly. If the user wants screenshots later, add them as a post-v1 ticket the user captures themselves.
- **[major]** ux.md 12.2 / concern C9 vs ARCHITECTURE.md 13 ('Window close => preventDefault(); hide()'); contracts.md section 8 (`app:ackTrayHint`, view `tray_hint`)
  - Problem: The requirement is 'X hides the app to hidden icons'. ARCHITECTURE 13 promises hide + an in-window coach mark (impossible in a hidden window); ux.md resolves it by NOT hiding on the first X (window stays up to 12 s until 'Got it'), and contracts.md bakes that in with `app:ackTrayHint`. Three binding documents now disagree, and the first user experience of the X button contradicts the locked behaviour.
  - Fix: Make ARCHITECTURE 13 the rule: every X click hides immediately (`preventDefault(); hide()`). On the first hide show the Windows toast (already specified) and set `meta.tray_hint_seen`; show the in-window coach mark the next time the window is opened (the alternative reading already drafted in ux.md 12.2). Keep `app:ackTrayHint` only to dismiss that coach mark; delete the 'keep the window visible' sentence from ux.md 12.2 and C9, and add the e2e assertion 'first close hides within 200 ms' to tray-lifecycle.spec.ts.
- **[minor]** ARCHITECTURE.md 7 (`ux_items_open` covers only needs_reply/info_missing; 'an in_calendar item does not block a new open item') + 6.5 ('supersede the item's older pending actions'); ux.md 6.7 ('In calendar' row keeps 'Approve & send' for the unsent draft)
  - Problem: An `in_calendar` item with an unsent draft keeps a live `send_reply` action. When the contact writes again, a new open item is created for the same chat with a fresh draft; the supersede rule is per item, so two approvable, mutually stale drafts now exist for one chat and either can be sent. This weakens the 'recipient/content the user saw' guarantee in spirit and confuses the dashboard.
  - Fix: When Ingest creates a new open item for a chat, supersede every pending `send_reply` action of that chat's non-open items (one extra UPDATE in the same transaction) and drop the collapsed 'Reply not sent yet' affordance on `in_calendar` cards once superseded. Add this case to pipeline-states.test.ts.
- **[minor]** agent-pipeline.md section 2, `sanitizeForModel` code block (the `.replace(/[‪-‮⁦-⁩]/g, '')`, zero-width and C0 lines)
  - Problem: The regex character classes are written with the literal invisible code points (bidi controls, zero-width chars, C0 controls) instead of `\u` escapes. Anyone pasting the spec into `agent/sanitize.ts` gets classes whose contents depend on how the editor/Markdown pipeline preserved the invisible bytes; the C0 class in particular renders as `[ --]` and will match a space-to-hyphen range, not control characters. The I5/sanitiser tests could then pass against the wrong set.
  - Fix: Rewrite the block with explicit escapes: `/[\u{E0000}-\u{E007F}]/gu`, `/[‪-‮⁦-⁩]/g`, `/[​-‍⁠﻿]/g`, `/[ --]/g`, and add a unit test that asserts each listed code point is removed while U+200E/U+200F survive.
- **[minor]** contracts.md section 4 `CLAUDE_MODEL_PRESETS = ['claude-opus-5','claude-sonnet-5','claude-haiku-4-5']`; ARCHITECTURE.md 8 ('dropdown from client.models.list() - never a hard-coded list', 'claude-haiku-4-5 may retire after 2026-10-15')
  - Problem: The contract freezes a hard-coded preset list containing a model the architecture itself expects to retire within weeks, contradicting the 'never a hard-coded list' rule and guaranteeing a MODEL_NOT_FOUND path for a preset shown in the UI.
  - Fix: Keep presets as UI ordering hints only: intersect `CLAUDE_MODEL_PRESETS` with the live `models.list()` result before rendering, hide missing ones, and drop `claude-haiku-4-5` from the constant (or mark it `{ id, sunset: '2026-10-15' }` and filter by date).
- **[minor]** ux.md 6.8 ('Copy: writes the current textarea content with navigator.clipboard.writeText from the click handler') vs contracts.md section 17 #4 / IPC `clipboard:writeText` (all renderer permission requests denied)
  - Problem: The UX spec still instructs lane 15 to use `navigator.clipboard`, which the hardened window blocks; the contract already moved Copy to a main-process IPC. Two binding documents give different implementations for the same MUST feature ('Copy' escape hatch on every card).
  - Fix: Change ux.md 6.8 and 14.3 to call `api.clipboardWriteText(text)` (IPC `clipboard:writeText`), keep the 'Copied' label behaviour, and add the jsdom test that the click sends exactly one `clipboard:writeText` with the textarea value.
- **[minor]** ARCHITECTURE.md 9 (llama-server spawn defaults `-ngl auto`, `--fit on`; CPU fallback only after a FAILED self-test) and 17 (iGPU memory never counted for the tier)
  - Problem: On the primary laptop target (CPU + Intel/AMD iGPU, no dGPU) the Vulkan build offloads to the iGPU by default. The research cites both cases: iGPU offload can be several times faster, but Intel Vulkan drivers also produce slow-but-not-failing runs. The design only switches to `--device none` on failure; a slow iGPU path is reported as 'below 5 tok/s -> suggest a smaller model', which pushes the user to a worse model instead of the faster CPU path. 'Local ready to use on a laptop' is then met with a needlessly weak model.
  - Fix: In the first-run self-test on machines with no dedicated GPU, time the fixed prompt twice (auto vs `--device none`, ~10 s each), persist the faster mode in `settings.llm.local.forceCpu`, store both numbers in `model_files.bench_json`, and only suggest a smaller tier when the better of the two is below 5 tok/s.
- **[minor]** Scope creep across ARCHITECTURE.md 5.3 (`list_events` + `settings.calendar.shareTitlesWithAi`), 12.2 (`chat policy local_only`, `notifications: with_name`, `cloudDailyTokenBudget` + footer usage counter, IANA time-zone picker), ux.md 6.10 (IgnoredDrawer with Restore), 13.2 (Alt+P / Ctrl+L / Ctrl+, / F6 shortcuts + 'Keyboard shortcuts' disclosure), contracts.md `chat:listPolicies`, `dashboard:getIgnored`

In particular `list_events` is the only tool that ships calendar titles to a cloud provider and exists solely to serve a default-off setting; `local_only` is a third per-chat policy nobody requested; the Ignored drawer is effectively a fourth dashboard list.
  - Fix: Cut for v1: `list_events` tool + `shareTitlesWithAi` (free/busy is enough for drafting); `local_only` policy and its `held/local_only` hold reason; `notifications.with_name` (keep off/generic); the Alt+P/Ctrl+L/Ctrl+, shortcuts (keep F6 and Escape); the IANA time-zone picker (use the OS zone, show it read-only). Keep the Ignored drawer only as 'Undo dismiss' (last 20 dismissed) or drop it and rely on the 6 s undo toast. Record each cut in ops/DECISIONS.md and remove the matching rows from the ownership matrix and the locale seed list.

## critic:security — 17 findings

- **[major]** docs/ARCHITECTURE.md 4.3 (host state machine: `stdout "Device logged out" => stop`, `stdout "Client outdated" => terminal BRIDGE_OUTDATED`, `REST API server error => kill + new port`) and 4.4; docs/specs/contracts.md §12 `bridge/stdoutMarkers.ts` (`matchMarkers(chunkUtf8)` = substring match after ANSI strip)
  - Problem: Bridge stdout is UNTRUSTED per the taint rule, yet substring markers on it drive state transitions with side effects. The vendored bridge prints every live message verbatim to stdout (`vendor` source main.go:1709-1711: `fmt.Printf("[%s] %s %s: %s\n", timestamp, direction, sender, content)` and the media-filename variant), and content may contain newlines. A contact who sends the text `Client outdated` puts the app into the no-respawn terminal state BRIDGE_OUTDATED (sending disabled until an 'app update'); `Device logged out` stops the bridge and offers 'Re-link', which deletes `store\whatsapp.db` (the session keys) on one click; `REST API server error:` triggers kill+respawn up to 3 times; `History sync complete.` is harmless. This is a zero-cost remote DoS of the WhatsApp link plus a social-engineering path to make the user re-pair.
  - Fix: Never let a stdout marker cause a state transition that has a side effect. Keep stdout only for benign hints (readiness `Starting REST API server`, `History sync complete` -> scan poke). Derive `logged_out` solely from `GET /api/pairing/status` (`status:'error'` + LOGGED_OUT_MESSAGE_RE) and `outdated`/`unstable` from observable facts (health 503 persisting -> respawn -> breaker), with `client_outdated`/`rest_error` markers used only to annotate the ErrorCode shown when the breaker opens. If any stdout marker must stay authoritative, require (a) the exact whatsmeow line framing `^\d\d:\d\d:\d\d\.\d{3} \[Client (INFO|WARN|ERROR)\] ` at the start of a line that does NOT begin with the message-echo prefix `[YYYY-MM-DD HH:MM:SS] ←`, and (b) corroboration by REST within 5 s. Add a security test: an inbound message whose text equals each marker string produces no state change (extend `bridge-lifecycle.test.ts` and the injection corpus with a `stdout_marker` vector).
- **[major]** docs/specs/contracts.md §14 `ActionExecutor.approve` step order (pending check -> ... -> fresh free/busy (await) -> rate limits -> write-ahead) and §15.1 `repos.actions.markApprovedExecuting/markFailed/markDone`; docs/specs/contracts.md §15.2 `trg_actions_state`
  - Problem: Two concurrent `action:approve` invocations for the same `create_event` action both pass the `state='pending'` check, both await the free/busy pre-check, then A commits pending->approved->executing and calls MCP. B's write-ahead hits the trigger (`OLD.state<>'pending'`) and throws; the spec does not say what B does with that exception. If B's catch-all follows the documented `-> failed(error_code) + fresh pending clone` path, `executing -> failed` is allowed by the trigger, so B marks A's in-flight action `failed` while A is still creating the event, A's later `markDone` aborts ('bad done'), the card shows 'Sending failed / Try again' with a fresh clone, and the user's next click produces a second event (or a second WhatsApp send if the jitter sleep sits before the write-ahead). The same interleaving exists for `send_reply` if any `await` (jitter, rate-limiter) precedes the write-ahead. The test plan asserts 'exactly one side effect' but the contract does not specify the mechanism.
  - Fix: Specify compare-and-set semantics in `repos.actions`: `markApprovedExecuting` = one transaction with `UPDATE actions SET state='approved',approved_at=?,approved_final_json=? WHERE id=? AND state='pending'`, assert `changes===1` else return `ACTION_STALE` (no clone, no audit 'failed'); `markDone/markFailed/markUnknownOutcome` all `WHERE id=? AND state='executing'` with `changes===1` asserted. Add an in-memory `inFlight: Set<ActionId>` in the executor checked synchronously before the first `await`. State explicitly that a trigger abort or CAS miss is a gate failure (Result.ok=false ACTION_STALE) and never enters the `failed`/clone path. Put the send jitter after the write-ahead (it already is `executing`) and never before it. Extend `approval-binding.test.ts` 'double click' to a create_event with a slow fake free/busy so the interleaving actually happens.
- **[major]** docs/ARCHITECTURE.md A11 ('write-ahead states ... enforced by a SQLite trigger') and §10 `trg_actions_state`; docs/specs/contracts.md §15.2 same trigger and 'Architecture concerns' #8 (raised, not adopted)
  - Problem: The trigger is the only DB-level enforcement of approval-first, but it permits `executing -> pending`, `failed -> pending` and `unknown_outcome -> pending`. Any of these re-arms an already-approved (or already-executed) action so a later `pending -> approved -> executing` re-executes the same side effect without a new proposal, defeating the 'a crash never duplicates a side effect' invariant (I7) at the layer that is supposed to hold when application code is buggy. It also allows `executing -> failed` from a second caller (see the race finding) and `approved -> executing` without `approved_final_json`.
  - Fix: Harden the trigger text (it is a migration, so decide now): add `WHEN NEW.state='pending' THEN RAISE(ABORT,'cannot return to pending')`, add `'failed'` to the terminal list (the retry-clone model makes it terminal), add `WHEN NEW.state='executing' AND NEW.approved_final_json IS NULL THEN RAISE(ABORT,'no final payload')`, and add `approved_final_json` to `trg_actions_frozen` once state is past `approved` (e.g. a second trigger `BEFORE UPDATE OF approved_final_json ... WHEN OLD.state IN ('executing','done','failed','unknown_outcome')`). Add each new illegal transition to the `db/*` trigger test table and to `approval-binding.test.ts` ('direct SQL `UPDATE actions SET state='pending'` on an executing row aborts').
- **[major]** docs/ARCHITECTURE.md §8 'keys ... passed explicitly (stray env vars ignored), never in URLs'; docs/specs/test-strategy.md 5.3 rows `llm/claude.ts` ('`ANTHROPIC_API_KEY` env ignored') and `llm/gemini.ts`
  - Problem: Only the API-key env vars are called out. `@anthropic-ai/sdk` also reads `ANTHROPIC_BASE_URL` from `process.env` when `baseURL` is not passed, and `@google/genai` reads `GOOGLE_GEMINI_BASE_URL` (and `GOOGLE_API_KEY`/`GEMINI_API_KEY`). The main process inherits the user's environment; on a developer machine (this user's) such variables commonly point at a proxy/gateway, and any same-user process can set a per-user env var. Result: the decrypted API key plus the full chat payload are silently sent to a non-Anthropic/non-Google host, with no consent screen mention and no log line.
  - Fix: Construct both SDK clients with explicit constants: `new Anthropic({ apiKey, baseURL: 'https://api.anthropic.com', maxRetries: 2, timeout: 60_000 })` and `new GoogleGenAI({ apiKey, httpOptions: { baseUrl: 'https://generativelanguage.googleapis.com' } })`; never pass `undefined` for these. Add to the `consent-payload.test.ts` snapshot: with `ANTHROPIC_BASE_URL=https://evil.example` and `GOOGLE_GEMINI_BASE_URL=https://evil.example` in `process.env`, the recording SDK double sees the constant base URLs. Also list `NODE_EXTRA_CA_CERTS`, `HTTPS_PROXY`, `SSL_CERT_FILE` as variables the app must not propagate to children (bridge/llama/MCP minimal env already exclude them; document it for the main process as accepted R4 residual).
- **[major]** docs/specs/contracts.md §11 `mcp/readClient.ts`: `McpToolCaller` type and `createMcpReadClient(call: McpToolCaller)`; docs/ARCHITECTURE.md A9/A22 and I2 'capability separation by construction'
  - Problem: The single raw `McpToolCaller` value (able to call `create-event`, `manage-accounts`) is handed by `compose.ts` to all three facade constructors, including the READ facade that the LLM loop reaches through ToolGate. The 'no write method' guarantee therefore rests on the body of `readClient.ts` never passing a non-read name into `call(...)`; a one-line bug or a future 'reconcile' helper in that file can execute `create-event` with LLM-influenced timing/arguments from inside the S3 loop, and neither the import-graph test nor the ToolGate name table would notice.
  - Fix: Narrow the capability at the host boundary: `McpHost` exposes `callerFor(cls: McpToolClass): McpToolCaller` that returns a wrapper which asserts `MCP_TOOLS[tool] === cls` at runtime (throws + audit `tool_blocked` otherwise) and is the only value `compose.ts` passes to each facade (`createMcpReadClient(host.callerFor('read'))`, `createMcpWriteClient(host.callerFor('write'))`, `createMcpAdminClient(host.callerFor('admin'))`). Type the facade parameters as `McpToolCaller<'read'>` etc. (generic over the allowed name union) so the mismatch is also a compile error. Add a `tool-gate.test.ts` case: a monkey-patched read client calling `create-event` through its injected caller is rejected before reaching the fake MCP.
- **[major]** docs/ARCHITECTURE.md 5.4 (`eventId` = base32hex(sha256(actionId)) 'a retry can never create a second event') and 6.6 ('Send again (new action, new click)'); docs/specs/contracts.md §1 `ApprovalAction.attempt/retryOf`, §14 `eventIdFor(actionId)` and lifecycle ('not found -> stays unknown_outcome + fresh pending clone')
  - Problem: Retry clones get a fresh uuid `actionId`, so `eventIdFor(clone) !== eventIdFor(original)`. When a `create-event` call times out or the app crashes after Google accepted it but reconcile cannot find the event (MCP down, token expired, eventual consistency, reconcile window mismatch), the card offers 'Add again'; the clone creates a second event with a different id, and Google's duplicate detection is only a similarity heuristic (`allowDuplicates:false`, threshold 0.7). The I7 claim 'never duplicates a side effect' does not hold across the clone chain, which is exactly the path that exists for recovery.
  - Fix: Derive the deterministic id from the retry-chain root: `eventIdFor(rootActionId)` where root = follow `retry_of` to the first action (or, simpler and equivalent, from `${itemId}:create_event:${proposalVersion}` = the idempotency key without the `:rN` suffix). Then a clone re-sends the same `eventId`; Google answers 409 'already exists' for an event that really was created, which the executor maps to `done` (+ reconcile fills htmlLink) instead of creating a second event. Add to `crash-recovery.test.ts`: unknown_outcome -> reconcile fails (fake MCP `crash_on_call:list-events`) -> 'Add again' -> fake MCP receives the same `eventId` and rejects -> exactly one event.
- **[minor]** docs/ARCHITECTURE.md A13 and 4.6 step 4 (`is_known = EXISTS(SELECT 1 FROM messages WHERE chat_jid=? AND is_from_me=1)`); docs/specs/contracts.md §12 `BridgeDb.userHasSentIn`
  - Problem: The unknown-sender gate exists to remove the zero-cost stranger attack, but the bridge stores the user's own reactions as message rows with `is_from_me=1, media_type='reaction'` (main.go:1586-1589). One thumbs-up tapped on the phone to a stranger's message (near-zero effort to socially engineer) flips the chat to 'known' and every later message from that stranger is LLM-processed and, with a cloud provider, sent to the cloud - without the 'Analyse this chat' click the design promises. The same applies to a `deleted_at` row and to an empty-content row.
  - Fix: Define `userHasSentIn` as `EXISTS(SELECT 1 FROM messages WHERE chat_jid=? AND is_from_me=1 AND (media_type IS NULL OR media_type <> 'reaction') AND content <> '' AND deleted_at IS NULL)` and add a `fake-bridge-db` test: an own reaction row does not make a chat known; an own text row does.
- **[minor]** docs/ARCHITECTURE.md §10 retention job ('`item_messages.text`, `proposals.draft_text/extraction_json/event_json` nulled after retentionDays; closed items after 90 days') and backups (`VACUUM INTO backups\app-YYYYMMDD.db`, keep 3); docs/specs/contracts.md §15.2 `actions.canonical_json`, `approved_final_json`, `proposals.freebusy_json`
  - Problem: The sent message text and the event title/location live verbatim in `actions.canonical_json` and `actions.approved_final_json` (and the calendar busy blocks in `proposals.freebusy_json`), none of which the retention job touches, so with `retentionDays=7` the text survives until the closed item is deleted at 90 days. - **[minor]** docs/ARCHITECTURE.md §10 `audit_log` ('kinds: tool_blocked ... metadata only') and §14 logging ('tool names' allowed); docs/specs/test-strategy.md 8.2 item 1 ('300-char name => blocked ... `audit_log tool_blocked` rows'); docs/specs/contracts.md §15.1 `runs.error_code`, `triage_queue.last_error TEXT`
  - Problem: A blocked tool name is model output, i.e. attacker-influenced text (the tests themselves feed 300-char and homoglyph names). - **[minor]** docs/ARCHITECTURE.md §11 `external:open` ('event link validated against `https://(www|calendar).google.com/`'); docs/specs/contracts.md §1 `Item.calendarHtmlLink` comment; docs/ARCHITECTURE.md §2 taint rule ('MCP tool results ... never in `shell.openExternal`')
  - Problem: `htmlLink` comes from an MCP tool result, which the design classifies UNTRUSTED, and is the one value from outside the app that reaches `shell.openExternal`. The check is written as a prefix regex with unescaped dots and no host boundary: `https://www-google.com/...` and `https://wwwXgoogle.com/...` match `(www|calendar).google.com/`. Even a correct hostname check lets an open-redirect on google.com (`/url?q=`) through if a compromised/garbage MCP response supplies the link.
