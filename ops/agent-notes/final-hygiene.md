## 1. REQUEST 3 - permanent L3 guard for the consent-to-bridge-start defect

### 1.1 What landed

`tests/integration/consent-starts-bridge.test.ts` (new, 4 tests, ~0.25 s) over the real `compose()` through
`tests/helpers/harness.ts`, attach mode, in-process fake bridge. The positive spec is the one from
`repair-compose-defects.md` section 1.1, slightly extended:

1. **starts the bridge without a restart** - harness with `profile: { whatsappTos: false, onboardingDone: false,
   paired: false }`, fake bridge in `qr_pending`. Asserts `app.started()`, no current `whatsapp_tos` consent, and
   `health().whatsapp.state === 'not_started'` - and that two more poll rounds of pure time leave it there (the defect
   was that *nothing* ever moved it). Then `invoke('consent:accept', { kind: 'whatsapp_tos', version })` -> `ok`,
   consent current; after two virtual seconds the state is no longer `'not_started'`; after six 20 s polls
   `pairing:get` reports `'qr_pending'`, a `pairing` push with `qr_pending` was emitted, `whatsapp.code` is not
   `WA_TOS_REQUIRED`, and no `bridge_start_after_consent_failed` line was logged.
2. **idempotent** - same fresh profile with the fake `connected`: first accept -> `'online'`; a second accept is `ok`,
   the state stays `'online'` and `meta.last_online_ts` is unchanged (compose writes it on every edge away from online,
   so an unchanged value proves no stop/restart happened).
3. **only the WhatsApp disclosure starts the bridge** - fresh profile with `cloudConsent: false`; accepting
   `cloud_claude` is `ok` and the bridge stays `'not_started'`. Guards the `req.kind === 'whatsapp_tos'` condition.
4. **a rejected consent starts nothing** - version `current + 1` -> `ok: false` (BAD_REQUEST per `[R2]` in
   `src/shared/ipc.ts`), consent not current, bridge `'not_started'`. Guards the `res.ok` condition.

### 1.2 One thing the original spec sketch did not say

The attach-mode launcher (`compose.ts` `createAttachedBridge()`) maps `/api/health` to **`online` / `reconnecting`
only** - `needs_pairing` is a spawning-launcher state. So with the fake in `qr_pending` the health state after the fix
is `'reconnecting'`, not `'needs_pairing'`; the QR phase is reported by the pairing poller, which is exactly what the
Link-WhatsApp panel reads through `pairing:get`. My first draft asserted `'needs_pairing'` and failed on that - the
committed test asserts `not 'not_started'` plus `pairing:get === 'qr_pending'`, which is the product behaviour the
wizard depends on. Not a product defect; recorded so nobody re-derives it.

## 2. `tests/fakes/fake-bridge.ts` - `inbound` / `outboundFromPhone` revive `ts`

- New `withRevivedTs(args)`: returns `args` untouched when `ts` is absent (the fake then picks its own now, as before)
  and `{ ...args, ts: reviveDate(args.ts) }` otherwise. Both verbs go through it; `historySync` already revived per
  row and is unchanged. `reviveDate` is now **exported** (no behaviour change) so it can be unit-tested directly.
- Test: `tests/integration/fake-bridge-control.test.ts` (new, 5 tests, ~0.6 s):
  - `reviveDate` direct: Date passthrough (same object), ISO string and epoch number -> same instant, and
    `'nope' / NaN / Infinity / null / undefined / {} / true` all throw `fake-bridge control: not a timestamp: <json>`.
  - **Child-mode round trip** - the system `node` runs `tests/fakes/fake-bridge.ts --control-port … --control-secret …`
    exactly as `WCA_BRIDGE_CMD` does in e2e (cwd = a temp dir, `WHATSAPP_BRIDGE_PORT=0`, a 64-char test token, no
    webhook). `inbound` with an ISO `ts`, `outboundFromPhone` with an epoch `ts`, `inbound` without `ts`: all 200, and
    the three rows read back from `<cwd>/store/messages.db` carry the right instants (parsed from the go-sqlite3
    text) and `is_from_me`. Then `exit` -> 200 and exit code 0 (bridge-contract section 8).
  - Malformed `ts` (`'nope'`, an object) on either verb -> **500** `{"error":"… not a timestamp …"}`, no row written,
    child still alive and serving `exit` afterwards.
  - Proof it catches the defect: with only the export in place (verbs unfixed) the round-trip test failed with
    `{"error":"date.getTime is not a function"}` / status 500 on the first `inbound`; with the fix, 5/5 pass.
- T7: the child is tracked by the spawn guard; the `afterEach` sends `exit` (or kills) and awaits the exit event, so
  no leaked pid. T1: the spawn names only `node` and a `tests/fakes/` path. T3: all fetches are `127.0.0.1`.
