## REQUESTS (main / contract - not in this agent's surface)
1. ux-i18n-v2-3 (b): UX2 4.5 row `on` asks for Renew in the last 7 days and SetupStrip row 7 promises it, but `auto:requestEnable` refuses while any policy is live (autoPolicy.ts precondition: live -> BAD_REQUEST). Options: a `renew` flag on `auto:requestEnable` accepted only for an `on` policy within the window (fresh native dialog with `renew:true`, then replace the row), or change SetupStrip row 7 copy/action. Until then the renderer offers no Renew on `on` (a button that always fails would be worse).
2. ux-i18n-v2-4: persist the voice intent in main (e.g. a main-only flag set when enabled=true is refused for a not-ready tier, applied when the download completes) so the onboarding opt-in survives a restart mid-download.
3. ux-i18n-v2-5: main's `settings:set` does not guard `whatsapp.readTools.enabled`; a renderer (or a bug) can re-enable a stored `all_chats` scope without the native confirmation. Suggest: re-enabling with stored scope `all_chats` resets the scope to `trigger_chat` in main (or Off narrows the scope).
4. ux-i18n-v2-10: an `auto:listDecisions` read channel (shadow / fallback decisions) for the Automatic activity page during a trial.
5. ux-i18n-v2-2 / 11: distinct ErrorCodes would remove the renderer's inference (rate limit vs provider vs snapshot-changed BAD_REQUEST; v2-contracts.md:1757 specifies BAD_REQUEST for both antigravity and the 4th call). `cli:signIn` should `status.invalidate()` on CLI_NOT_INSTALLED / CLI_VERSION.
