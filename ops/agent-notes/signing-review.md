# signing-review - adversarial check of the signing pipeline + Defender gate (D-077, D-078, R11)

Date: 2026-10-04. Read-only review. Nothing was edited except this file. No build, signtool, installer or packaged exe
was run, and no certificate or store was touched. The checks that ran:
- `node scripts/sign-windows.mjs --plan dist/win-unpacked` (read-only header walk, 44 PE files);
- a Node `execFile` timeout probe with a SYNTHETIC thumbprint;
- `runDefenderGate` with a FAKE MpCmdRun runner on an empty scratch folder.

Files reviewed:
- `scripts/sign-windows.mjs`, `scripts/defender-scan.mjs`, `electron-builder.yml`;
- `src/main/bridge/invariants.ts` and `launcher.ts`, plus the `scripts/smoke-packaged.mjs` check 13 diff;
- `docs/WINDOWS-SECURITY.md`;
- electron-builder 26.15.3 internals: `platformPackager.js`, `winPackager.js`, `codeSign/windowsCodeSign.js`,
  `codeSign/windowsSignToolManager.js`, `targets/nsis/NsisTarget.js`, `targets/nsis/nsisUtil.js`, `vm/WineVm.js`,
  `builder-util/out/fs.js`.

## Findings (most severe first)

### MAJOR 1 - the bridge pin now comes from a writable text file, in UNSIGNED builds too
Where: `src/main/bridge/invariants.ts:43-64` (`selectBridgePin`), `src/main/bridge/launcher.ts:117-144`.

Before this change, the only acceptable bridge hash was the one compiled into `out/main` (inside app.asar). Now the
launcher reads `<resources>\bridge\SHA256SUMS` on EVERY build. Take a file with:
- one line `<any hash>  whatsapp-bridge.exe`;
- one line `# wca-signed-from <the public original pin>  whatsapp-bridge.exe`.

`selectBridgePin` then returns `<any hash>` as the pin. A local writer can therefore swap the exe and edit a two-line
text file. They no longer need to patch app.asar. This also holds in the default unsigned build. Its BYTES are
identical to before, but its RUNTIME trust is not. The signing-pipeline notes (hand-off 5) say this, but it ships
active today.

Fix:
- (a) Make the unsigned default identical to before. Compile a build-time flag, e.g. electron-vite
  `define: { __WCA_SIGNED_BUILD__ }` taken from WCA_SIGN_MODE at `npm run build`. With the flag false,
  `resolveBridgeExe` never reads the file. sign-windows `beforePack` refuses a mode/flag mismatch.
- (b) For signed builds, move the signed pin inside app.asar. electron-builder copies app.asar BEFORE extraResources
  (`platformPackager.js:218` vs `:238`), and `beforePack` runs before both. So `beforePack` (signing ON) can:
  - check the original pin;
  - sign a staged copy of the bridge outside the repo;
  - write its hash into `out/` so it lands in the asar.

  `sign()` then replaces the copied bridge bytes with that pre-signed copy instead of signing again (time stamps make
  signatures non-deterministic). The launcher reads the pin from the asar, never from `resources\bridge`.
- (c) Turn on `enableEmbeddedAsarIntegrityValidation` once signing is real.

### MAJOR 2 - the certificate thumbprint leaks into the error and build log when signtool times out or is killed
Where: `scripts/sign-windows.mjs:661`, `String(err.code ?? err.message)`.

When signtool is killed (the 10-min timeout, SIGTERM), `err.code` is `null`. The code then uses `err.message`, which
is `Command failed: <signtool> sign /sha1 <THUMBPRINT> ...`. That text is NOT passed through `redact()`.

Verified with a synthetic thumbprint. The probe printed the full argv, thumbprint included. electron-builder logs it a
second time (`winPackager.js:116-119`, "signing failed for file" warn with `e.message`).

This is realistic: SimplySign Desktop waiting for login or a PIN can hang signtool until the timeout. The agent's
"grep count 0" evidence used a stand-in that exited with code 1, so it never hit this path.

Fix: never use `err.message`. Use `err.code ?? err.signal ?? 'failed'`, and run the WHOLE message through `redact()`.
Add a unit test that makes a fake signer time out.

### MAJOR 3 - "provenance before signing" is tautological for llama, and for whisper's fallback and CRT files
Where: `scripts/sign-windows.mjs:383-398`.

The llama "pin" is the hash of `vendor/llama/win-x64-vulkan/<name>`, which is the very file the packaged copy was made
from. `vendor/` is gitignored and no per-file hash is committed: `vendor/llama.pin.json` pins only the zip.
`vendor/whisper/SHA256SUMS` is also gitignored, and the same fetch step writes it next to the binaries.

So a binary modified in `vendor/` after the fetch gets OUR signature. The claim "our signature never lands on an
unvetted binary" is true only for the bridge.

Fix:
- Commit per-file sha256 values (generated by `fetch-llama.mjs` / `fetch-whisper.mjs` from the pinned zip, e.g. a
  `files.sha256` map in `vendor/*.pin.json`) and compare against those.
- For the CRT DLLs, use `vcRedistCrt.files` (null = refuse), never "equals the vendor copy".

### MAJOR 4 - the Defender gate PASSES an empty or wrong tree, even with signing enforced
Where: `scripts/defender-scan.mjs:439-462`, `:172-187`, `:402-407`.

Take an existing but empty or truncated `dist/win-unpacked`, for example after a failed build:
1. MpCmdRun prints "found no threats", so the verdict is clean.
2. `listPeFiles` finds 0 files.
3. With 0 files there are 0 Authenticode failures, even when WCA_SIGN_MODE is set.
4. The gate exits 0 (PASS).

Verified with a fake runner on an empty scratch folder: exit 0, enforce true, 0 failures. The same happens when
win-unpacked is missing and only an installer is present: the gate scans the installer only and logs just a "note".

Fix:
- For a win-unpacked target, require the expected payload: `WhatsApp Calendar Agent.exe`, `resources/app.asar`,
  `resources/bridge/whatsapp-bridge.exe`, and a PE count floor (today 44).
- In enforce mode, 0 PE files is a failure.
- Optionally require that the "Scanning <path> found no threats" line names the target.

### MAJOR 5 - a partially signed tree, or a stale unsigned installer, passes the gate when WCA_SIGN_MODE is not set in the gate's shell; enforced mode accepts any publisher
Where: `scripts/defender-scan.mjs:159-165`, `:184`.

Enforcement depends only on the env of the shell that runs the GATE, not on what was built. Two cases pass with exit 0
("information only"):
- a failed signed build leaves `dist/win-unpacked` partly signed (signing-pipeline hand-off 6);
- a failed signed build leaves an unsigned installer in `dist/`, because makensis writes it before `signIf`.

When enforcement is on, any `Valid` signature from any CA passes. The gate does not check the signer CN or the time
stamp.

Fix:
- Also enforce when the target contains `resources/signing-manifest.json`. Also fail a "mixed" tree, where some of our
  files are Valid and some NotSigned (ignore Microsoft-signed DirectX DLLs).
- When enforcing, require signer CN == WCA_SIGN_PUBLISHER (when set) and a TimeStamperCertificate.
- Cross-check each manifest `signedSha256` against the on-disk hash.

### MINOR 6 - `WCA_SIGN_MODE=none` means different things in different places
Where: `scripts/sign-windows.mjs:133-136`; `scripts/defender-scan.mjs:164`; `docs/WINDOWS-SECURITY.md:67`.

The gate and the doc treat `none` as "unsigned". `readSigningConfig` rejects it with SigningConfigError, so the build
fails. Fail-safe, but the doc is wrong.

Fix: accept `none` in sign-windows as well, or remove it from the gate and the doc.

### MINOR 7 - building the NSIS installer on Windows EXECUTES a freshly built, unsigned NSIS stub
Where: `NsisTarget.js:337-375` -> `WineVm.js:28-29` (`exec(target)` directly on win32).

This is pre-existing electron-builder behaviour, not caused by this phase. To extract the uninstaller, the build writes
an uninstaller-generator exe to the installer path and RUNS it. So D-078's "building is not running" is not literally
true for `electron-builder --win`. defender-gate's builds 1 and 2 ran such a stub twice.

Fix: record this in DECISIONS/NOTES. If the rule must be strict, agent phases build `--dir` only and the user builds
the installer.

### MINOR 8 - Microsoft-signed DLLs are re-signed
`signExts: ['.dll']` makes signtool replace Microsoft's primary signature on `d3dcompiler_47.dll` and `dxil.dll`
(hand-off 4).

Fix: before signing, skip files that are already Valid with a Microsoft signer. Let afterSign accept those files on the
same Microsoft-signer check.

### MINOR 9 - electron-builder's own CSC_LINK path is still live in every mode
Where: `windowsSignToolManager.js` `cscInfo`, which runs for every signed file because our `sign` is a custom hook.

If `CSC_LINK` / `WIN_CSC_LINK` (+ `CSC_KEY_PASSWORD` / `WIN_CSC_KEY_PASSWORD`) is set in the shell, electron-builder
decodes or downloads the .pfx to a temp file and opens it with the password (`importCertificate`, `getCertInfo`). This
happens even with WCA_SIGN_MODE off. No store is touched on Windows, but a key file and its password are handled
outside this pipeline.

Fix: `beforePack` refuses, in every mode, when any of CSC_LINK, WIN_CSC_LINK, CSC_KEY_PASSWORD,
WIN_CSC_KEY_PASSWORD or CSC_NAME is set. Checking the names only reads nothing.

### MINOR 10 - "Valid" does not mean "accepted by Smart App Control"
Where: `scripts/sign-windows.mjs:426-445`.

A locally trusted certificate (self-signed or private root) gives `Valid` on this PC. A misconfigured build would pass
afterSign and the Defender gate while SAC still blocks it.

Fix: state this in README / WINDOWS-SECURITY "after signing". The release checklist needs a real SAC launch test on a
clean machine. Any chain or root inspection would read a certificate store, so it needs explicit user approval.

### MINOR 11 - signed builds have no green path yet, and a rejected pin file gives no diagnostic
- Smoke checks 4 and 7 compare against the ORIGINAL pins (signing-pipeline hand-off 2), so they fail on any signed
  tree.
- `resolveBridgeExe` drops `pin.source` (`launcher.ts:143`). With a bad pin file, a signed build fails as
  BRIDGE_BINARY_BLOCKED and gives no clue why.

Fix: implement the manifest-based smoke rule from hand-off 2, and log `pin.source` (no hash needed).

### MINOR 12 - the two PE detectors disagree
- `sign-windows.mjs:292` rejects `e_lfanew < 64`, but the Windows loader accepts small offsets (tiny / overlapping
  headers). A crafted PE with a non-.exe/.dll name could escape afterSign's completeness walk.
- `defender-scan.mjs:189-196` reads only 4 KiB, so it misses `e_lfanew > 4092` unless the extension matches.

Fix: one shared helper, lower bound 4, read the signature at `e_lfanew` directly.

## Checked and found sound (no finding)
- **OFF mode.** Every hook returns before any I/O. electron-builder uses our `sign` as the executor
  (`windowsSignToolManager.js:132-159`), so its own signtool path never runs.
- **afterSign always runs.** `signApp` returns true (`platformPackager.js:334`), so the "skipping afterSign" branch is
  not hit.
- **Hook order** (26.15.3):
  1. app.asar;
  2. extraResources, signed at copy time (no hard links: `builder-util fs.js:217` turns them off whenever a
     CopyFileTransformer is returned, and on win32 anyway);
  3. fuses;
  4. signApp;
  5. afterSign (re-pin + manifest);
  6. NSIS: elevate copy + sign, uninstaller, installer;
  7. artifactBuildCompleted.

  The re-pin is in place before the NSIS archive is made.
- **A sign failure fails the build.** `signIf` returns the rejecting promise; only the queue swallows it
  (`winPackager.js:115-121`).
- **Partially signed tree inside electron-builder.** Refused by afterSign and artifactBuildCompleted. A file skipped by
  the exe build cache (`copyIfValid`) would show up as NOT SIGNED.
- **Re-pin.** A signed build never runs against the UNSIGNED hash: the launcher accepts exactly one hash, rejects a
  "signed" hash equal to the original, and a missing or broken re-pin fails closed. No launcher path accepts "any
  signed file". The weakness is MAJOR 1, which is about where the hash comes from.
- **Gate verdicts.** Timeout, spawn failure, `Failed with hr`, unrecognised output and a missing positional path all
  give exit 4, never 0. A missing Authenticode record counts as a failure when enforcing.
- **Stores and settings.** Nothing writes a certificate store or a Defender setting. Only these run:
  - `signtool sign /sha1` (reads CurrentUser\My);
  - `Get-AuthenticodeSignature`;
  - `MpCmdRun -Scan -ScanType 3 -File <p> -DisableRemediation`.

  There is no exclusion, quarantine or preference token.
- **Secrets.**
  - The thumbprint is never written to a file. It appears only in signtool's argv, which `/sha1` needs; it is a public
    identifier but visible in process listings.
  - It is redacted from signtool output, apart from MAJOR 2.
  - The azure `metadata.json` holds no secret, and Azure credentials are never read.
